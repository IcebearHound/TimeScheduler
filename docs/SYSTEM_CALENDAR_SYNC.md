# 系统日历提醒

在 **设置 → 系统日历提醒** 中开启自动同步，点击 **添加到系统日历**，在 iOS/macOS 等系统日历中确认订阅一次。后续每次打开网站、返回前台、恢复联网或修改日程，网站都会自动更新同一份订阅内容。也可点击“立即同步”。

系统日历负责刷新订阅及发送通知。网站无法强制 iOS 立即刷新，所以“最近更新订阅”表示服务端已收到日程，不表示手机已读取。需要即时生效的临近提醒，请在系统日历中核对。网站关闭后，已经被系统日历获取的提醒仍可由系统发出。

## 首次设置

1. 开启自动同步并生成订阅。
2. 点击“添加到系统日历”，确认订阅。如果链接未唤起日历，在 iOS 系统设置搜索“添加订阅日历”，粘贴复制的 HTTPS 链接。
3. 开启系统日历通知，并允许这个订阅的提醒；若出现“移除提醒”选项，应关闭该选项。
4. 核对一项未来事件的时间和提醒。实际刷新频率和通知行为取决于系统日历、系统权限及设备设置。

“下载日历文件”适用于手动导入。导入文件不会自动更新，多次导入可能造成重复；自动同步应使用订阅。

## 同步内容与规则

- 全部日程同步到一个独立订阅，包括课程、实验、作业和考试。实验课和考试保留开始/结束时间；作业、实验验收及报告以截止时间建立一分钟的日历事件。
- 已配置的事件提醒优先；没有配置提醒时使用面板中的默认提前时间。显式关闭的提醒不恢复为默认提醒。
- 已完成事项保留在日历中，但不带提醒；按节假日或自定义规则跳过的事项不进入订阅。
- 事件使用稳定 UID，修改时间、完成状态或提醒时替换同一个事件。删除日程会从订阅移除；完成和删除的效果需等待系统刷新。
- “停用并清空订阅”成功后停止自动发布，远端返回空日历。还应在系统日历中移除此订阅，以立即清理可能尚未刷新的旧提醒。

订阅包含日程名称、时间、地点、课程名称及提醒，不包含备注、作业内容或提交链接。订阅链接本身是读取凭据，持有者可读取内容；写入需要另一份随机密钥。密钥通过现有浏览器凭据库加密保存在本机 IndexedDB，不进入日程备份或账号同步。清除浏览器数据后将无法管理旧订阅，应先停用，或在系统日历中手动移除旧订阅。不同设备/浏览器分别建立订阅，避免同时订阅多份相同日程。

## 部署

前端静态托管本身无法保存供系统日历后台获取的订阅。功能复用项目现有 Cloudflare Worker，新增 Durable Object `CalendarFeedObject` 及 `CALENDAR_FEEDS` 绑定，迁移已写入 `worker/wrangler.jsonc`。

1. 将 `worker/wrangler.jsonc` 的 `APP_URL` 配置为实际前端地址；写入接口仅允许该 Origin。
2. 使用已有的 Cloudflare 部署身份运行 `npm run deploy:auth`，发布更新的 Worker 及 Durable Object 迁移。此命令也更新现有授权/AI 服务。
3. 前端构建设置 `VITE_CALENDAR_SERVICE_URL` 为该 Worker 根地址；未设置时使用现有 `VITE_AUTH_SERVICE_URL`。GitHub Actions 构建已接入同名 Repository Variable。也可在设置面板手动填入服务地址。
4. 重新构建并部署前端，然后按首次设置步骤建立订阅。

`GET /calendar/status` 可检查存储是否启用。订阅地址为 `/calendar/<读取令牌>.ics`，GET/HEAD 供系统读取；PUT/DELETE 需要正确的应用 Origin 和 Bearer 写入密钥。读取令牌是随机写入密钥的 SHA-256。每份订阅独立存储，单次上传上限 2 MiB、10,000 个事件；实际事件大小可能更早达到字节上限。此接口不依赖 GitHub/Gitee 登录。

## 验证

`npm test` 验证 ICS 编码、截止时间、完成/节假日规则、读写凭据隔离、版本更新及大日历存储。`npm run test:calendar-sync` 在隔离 Chromium 中验证 1440、390、320 像素宽度下的订阅、重新打开/前台同步、稳定 UID、修改提醒、完成任务、导出及停用，使用真实路由和内存存储。

这些检查不代表已部署 Cloudflare 或已在真实 iOS 系统日历上验收；上线后需使用实际设备确认订阅刷新及通知。
